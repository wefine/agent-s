# S2、S2.5、S3 任务规划与子任务拆分对比分析

## 1. 概述

本文档对比分析 S2、S2.5、S3 三个版本在用户输入规划和子任务拆分方面的设计差异、实现机制和适用场景。

## 2. 架构对比总览

| 特性 | S2 | S2.5 | S3 |
|------|-----|------|-----|
| **架构类型** | 层次化（Manager-Worker） | 无层次（仅 Worker） | 无层次（Worker + CodeAgent） |
| **规划方式** | 显式规划（DAG） | 隐式规划（LLM推理） | 隐式规划（LLM推理） |
| **子任务拆分** | 显式拆分（DAG节点） | 隐式拆分（单步执行） | 隐式拆分（CodeAgent调用） |
| **任务表示** | DAG（有向无环图） | 无结构化 | 无结构化 |
| **知识库** | 支持（任务级+子任务级） | 不支持 | 不支持 |
| **代码执行** | 不支持 | 不支持 | 支持（CodeAgent） |
| **重规划机制** | 支持（失败+完成） | 仅反射 | 仅反射 |
| **推理时间** | 较长 | 较短 | 中等 |

## 3. S2：层次化规划架构

### 3.1 核心设计理念

S2 采用**显式层次化规划**，通过 Manager（规划器）和 Worker（执行器）的分离实现任务分解和执行。

### 3.2 任务规划流程

```
用户输入任务
    ↓
Manager.get_action_queue()
    ├─ 知识检索（首次规划）
    │   ├─ 检索相似任务经验（Narrative Memory）
    │   ├─ 检索网络知识（可选）
    │   └─ 知识融合
    ├─ 生成步骤式计划
    ├─ 转换为 DAG
    └─ 拓扑排序生成子任务队列
    ↓
Worker.generate_next_action()
    ├─ 检索相似子任务经验（Episodic Memory）
    ├─ 反射评估
    ├─ 生成动作计划
    └─ 坐标转换
    ↓
执行动作
    ↓
[子任务完成/失败?]
    ↓ 是
触发重规划
```

### 3.4 优势与限制

**优势**：
- ✅ 结构清晰：显式的任务分解，易于理解和调试
- ✅ 依赖建模：通过 DAG 明确子任务依赖关系
- ✅ 经验复用：知识库系统支持任务和子任务级经验检索
- ✅ 错误恢复：支持失败后的重新规划

**限制**：
- ❌ 推理时间较长：需要额外的规划步骤
- ❌ 成本较高：规划阶段需要多次 LLM 调用
- ❌ DAG 转换可能不准确：依赖 LLM 的 DAG 生成能力

## 4. S2.5：无层次简化架构

### 4.1 核心设计理念

S2.5 采用**无层次架构**，直接由 Worker 生成动作，减少推理时间。

### 4.2 任务规划流程

```
用户输入任务
    ↓
AgentS2_5.predict()
    ↓
Worker.generate_next_action()
    ├─ [可选] Reflection Agent 评估轨迹
    ├─ Generator Agent 生成计划
    ├─ Grounding Agent 转换坐标
    └─ 执行动作
    ↓
更新历史记录
```

        Predict the next action(s) based on the current observation.

        agent = self.grounding_agent
        generator_message = (
            ""
            if self.turn_count > 0
            else "The initial screen is provided. No action has been taken yet."
        )

        # Load the task into the system prompt
        if self.turn_count == 0:

                self.generator_agent.system_prompt.replace(
                    "TASK_DESCRIPTION", instruction
                )

        reflection_thoughts = None

                text_content = textwrap.dedent(
                    f"""
                    Task Description: {instruction}
                    Current Trajectory below:
                    """
                )
                updated_sys_prompt = (
                    self.reflection_agent.system_prompt + "\n" + text_content
                )
                self.reflection_agent.add_system_prompt(updated_sys_prompt)
                self.reflection_agent.add_message(
                    text_content="The initial screen is provided. No action has been taken yet.",
                    image_content=obs["screenshot"],
                    role="user",
                )
            # Load the latest action
            else:
                self.reflection_agent.add_message(
                    text_content=self.worker_history[-1],
                    image_content=obs["screenshot"],
                    role="user",
                )
                full_reflection = call_llm_safe(
                    self.reflection_agent,
                    temperature=self.temperature,
                    use_thinking=self.use_thinking,
                )
                reflection, reflection_thoughts = split_thinking_response(
                    full_reflection
                )
                self.reflections.append(reflection)
                generator_message += f"REFLECTION: You may use this reflection on the previous action and overall trajectory:\n{reflection}\n"
                logger.info("REFLECTION: %s", reflection)

        # Add finalized message to conversation
        generator_message += f"\nCurrent Text Buffer = [{','.join(agent.notes)}]\n"
        self.generator_agent.add_message(
            generator_message, image_content=obs["screenshot"], role="user"
        )

        full_plan = call_llm_safe(
            self.generator_agent,
            temperature=self.temperature,
            use_thinking=self.use_thinking,
        )
        plan, plan_thoughts = split_thinking_response(full_plan)
        # NOTE: currently dropping thinking tokens from context
        self.worker_history.append(plan)
        logger.info("FULL PLAN:\n %s", full_plan)
        self.generator_agent.add_message(plan, role="assistant")

        # Use the grounding agent to convert agent_action("desc") into agent_action([x, y])
        try:
            agent.assign_coordinates(plan, obs)
            plan_code = parse_single_code_from_string(plan.split("Grounded Action")[-1])
            plan_code = sanitize_code(plan_code)
            plan_code = extract_first_agent_function(plan_code)
            exec_code = eval(plan_code)

            plan_code = "agent.wait(1.0)"
            exec_code = eval(plan_code)

        executor_info = {
            "full_plan": full_plan,
            "executor_plan": plan,
            "plan_thoughts": plan_thoughts,
            "plan_code": plan_code,
            "reflection": reflection,
            "reflection_thoughts": reflection_thoughts,
        }
        self.turn_count += 1

        self.screenshot_inputs.append(obs["screenshot"])
        self.flush_messages()

        return executor_info, [exec_code]

## 5. S3：无层次 + CodeAgent 架构

### 5.1 核心设计理念

S3 在 S2.5 的基础上增加了 **CodeAgent**，支持代码执行，实现 GUI 操作和代码执行的混合模式。

### 5.2 任务规划流程

```
用户输入任务
    ↓
AgentS3.predict()
    ↓
Worker.generate_next_action()
    ├─ [可选] Reflection Agent 评估轨迹
    ├─ Generator Agent 生成计划
    │   ├─ 决定使用 GUI Agent 还是 CodeAgent
    │   └─ 如果是 CodeAgent，调用 call_code_agent()
    ├─ CodeAgent 执行（如果调用）
    │   ├─ 执行 Python/Bash 代码（最多20步）
    │   ├─ 返回执行结果
    │   └─ 生成摘要
    ├─ Grounding Agent 转换坐标（GUI操作）
    └─ 执行动作
    ↓
更新历史记录
```

        - The code agent runs Python/Bash code in the background (up to 20 steps), independently performing tasks like file modification, package installation, or system operations.
        - After execution, you receive a report with:
            * Steps completed (actual steps run)
            * Max steps (step budget)
            * Completion reason: DONE (success), FAIL (gave up), or BUDGET_EXHAUSTED (used all steps)
            * Summary of work done
            * Full execution history
        - Interpretation:
            * DONE: The code agent finished before using all steps, believing the task was completed through code.
            * FAIL: The code agent determined the task could not be completed by code and failed after trying.
            * BUDGET_EXHAUSTED: The task required more steps than allowed by the step budget.

        ### Code Agent Verification
        - After the code agent modifies files, your job is to find and verify these files via GUI actions (e.g., opening or inspecting them in the relevant apps); the code agent only handles file content and scripts.
        - ALWAYS verify code agent results with GUI actions before using agent.done(); NEVER trust code agent output alone. If verification or the code agent fails, use GUI actions to finish the task and only use agent.done() if results match expectations.
        - **CRITICAL**: Files modified by code agent may not show changes in currently open applications - you MUST close and reopen the entire application. Reloading the page/file is insufficient.

        Never assume a task is done based on appearances-always ensure the specific requested action has been performed and verify the modification. If you haven't executed any actions, the task is not complete.

        ### END OF GUIDELINES
```

### 5.4 优势与限制

**优势**：
- ✅ 代码执行能力：支持 Python/Bash 代码执行，处理复杂数据操作
- ✅ 混合模式：GUI 操作和代码执行相结合
- ✅ 子任务拆分：通过 CodeAgent 调用实现隐式子任务拆分
- ✅ 验证机制：CodeAgent 结果需要 GUI 验证

**限制**：
- ❌ 无知识库：无法复用历史经验

- ❌ 验证复杂性：需要 GUI 验证代码执行结果

## 7. 适用场景分析

### 7.1 S2 适用场景

**适合**：
- ✅ 复杂任务：需要明确任务分解和依赖关系
- ✅ 长期运行：需要知识库支持经验复用
- ✅ 结构化任务：任务可以明确分解为子任务
- ✅ 错误恢复：需要强大的错误恢复能力

**不适合**：
- ❌ 简单任务：规划开销过大
- ❌ 实时性要求高：规划延迟不可接受
- ❌ 成本敏感：多次 LLM 调用成本高

### 7.2 S2.5 适用场景

**适合**：
- ✅ 简单任务：快速执行，无需复杂规划
- ✅ 实时性要求高：推理时间短
- ✅ 成本敏感：单次 LLM 调用
- ✅ 灵活性要求高：动态调整策略

**不适合**：
- ❌ 复杂任务：无显式任务分解
- ❌ 需要经验复用：无知识库
- ❌ 数据操作：无代码执行能力

### 7.3 S3 适用场景

**适合**：
- ✅ 数据密集型任务：需要代码执行能力
- ✅ 混合任务：GUI 操作和代码执行结合
- ✅ 批量操作：代码执行效率高
- ✅ 文件处理：代码执行更适合

**不适合**：
- ❌ 需要经验复用：无知识库
- ❌ 需要显式规划：无显式任务分解
- ❌ 纯 GUI 任务：CodeAgent 开销不必要

## 8. 总结

### 8.1 设计演进路径

```
S2（层次化规划）
    ↓ 简化
S2.5（无层次简化）
    ↓ 增强
S3（无层次+CodeAgent）
```

**演进特点**：
1. **从显式到隐式**：从显式规划到隐式 LLM 推理
2. **从复杂到简单**：从层次化架构到扁平化架构
3. **从单一到混合**：从纯 GUI 操作到 GUI+代码执行

### 8.2 核心差异总结

1. **规划方式**：
   - S2：显式规划（DAG）
   - S2.5/S3：隐式规划（LLM推理）

2. **子任务拆分**：
   - S2：显式拆分（DAG节点）
   - S2.5：隐式拆分（单步执行）
   - S3：隐式拆分（单步执行+CodeAgent调用）

3. **知识管理**：
   - S2：完整的知识库系统
   - S2.5/S3：无知识库

4. **执行能力**：
   - S2/S2.5：仅 GUI 操作
   - S3：GUI + 代码执行

5. **错误处理**：
   - S2：重规划机制
   - S2.5/S3：反射机制

### 8.3 选择建议

- **选择 S2**：需要复杂任务规划、经验复用、错误恢复
- **选择 S2.5**：需要快速执行、简单任务、成本敏感
- **选择 S3**：需要数据操作、代码执行、混合任务

三个版本各有优势，应根据具体任务需求选择合适的版本。
